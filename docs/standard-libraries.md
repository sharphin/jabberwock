# 標準ライブラリとWindows向け描画・GUIの実装方針

状態: 実装に先立つ設計。以下のAPI名と内部表現は提案であり、利用できる機能の一覧ではない。
既存のコンパイラ・aliceの動作は、この文書の追加では変更しない。

## 合意した範囲

- ファイル入出力、通信、PostgreSQL、GUIを扱いたい。
- GUIはWindowsを先行し、ゲームの描画にも使いやすい形式にする。Linuxは今後検討する。
- Windowsのウィンドウと入力はWin32、描画はDirect3D 11、文字の組み立てはDirectWriteを使う方向。
- 今回の安全性検証1〜7を保ち、新しい機能にも同じ検証を加える。

ここから先の細部は実装方針の提案。公開APIと配布方法は実装時に仕様書へ反映する。
最初のGUI対応環境はWindows 10 1809以降/Windows 11の64ビットを想定する。

## 現在の実装との差

| 対象 | 現在あるもの | 新しく必要なもの |
|---|---|---|
| ファイル | `read_file` / `write_file` によるUTF-8の一括読み書き | バイナリ、開いたファイル、逐次読み書き、位置変更、明示的なflush/close、ディレクトリ |
| 通信 | OSソケットを扱う公開APIなし | TCP、DNS、タイムアウト、接続終了、TLS。その上にHTTPなど |
| PostgreSQL | ドライバなし | 接続、パラメータ付きSQL、結果の所有、NULL、トランザクション |
| 描画・GUI | ウィンドウと描画の公開APIなし | イベント、描画、文字、レイアウト、入力部品 |
| 資源の型 | `own` / `ref` とtask・channelの専用処理 | OS資源を偽造・複製できない不透明な型と解放処理 |
| alice | ローカルのパス依存、ソースとmanifestの更新時刻による再ビルド | 必要なパッケージだけのリンク設定、資源ABIを含むビルド指紋 |

`src/types.rs` に外部資源型はなく、公開された汎用FFIもない。
ユーザーが作る構造体のフィールドは型が公開されると公開されるため、`struct Window { i64 handle; }` のような
実装でOSハンドルを安全に隠せるとは扱わない。

現在は平坦なモジュールとパス依存を利用する。`use std.fs;` のような標準importを追加済みとはしない。
追加する記法、配布ルート、名前の衝突、選択式の同梱パッケージは [配置・読み込み仕様](standard-library-loading.md) に定める。
jwcはaliceのパッケージに未対応なので、自己ホスト側のパッケージ対応も別の作業として含める。

## 層の分け方

1. **コンパイラとruntimeの共通基盤**: 不透明な資源型、所有・借用・解放、エラー、スレッド制約。
2. **OS・外部ライブラリとの接続**: ファイル、ソケット、Win32、Direct3D、libpqを呼ぶ内部の処理。
3. **jabberwockのライブラリ**: 便利な読み書き、描画命令、レイアウト、SQL結果の変換など。
4. **aliceによる配布・ビルド**: 依存パッケージから必要な内部処理とリンク指定だけを選ぶ。

ファイル・通信を標準の基盤とし、GUI・PostgreSQLは必要なアプリが選ぶパッケージにする。
PostgreSQLを使わないプログラムにlibpqを要求せず、GUIを使わないCLIにDirect3Dのリンクを要求しない。
外部Rustクレートを使わない現在の方針を保つ。Windows SDKやlibpqなどのネイティブ依存は別に管理する。
公開された任意のC関数呼び出しを先に作る必要はなく、初期段階は用途を限定した内部APIにする。

## 共通の資源管理

### 所有と借用

File、TcpStream、PgConnection、Window、Textureなどは、不透明でムーブする資源型とする案を採る。
taskと同様、値自体が資源を所有する。公開APIで整数や生ポインタから資源を組み立てる関数を提供しない。
言語の型として資源の種類を区別し、ファイルをウィンドウとして使う操作も拒否する。

- コンストラクタは成功したときだけ所有値を返す。途中まで確保した資源は失敗経路で解放する。
- ムーブ後は元の値から利用できない。借用した値・読むだけの写しは所有権を取得しない。
- 正常なスコープ終了や通常のreturnで所有者が後始末する。写しの破棄でOS資源を閉じない。
- 明示的なcloseは結果を返す。close後の別名からの操作は、閉じた資源として拒否する。
- `ref mut` は排他的借用ではない。別名があることを前提に、操作のたびに状態を確かめる。
- runtime側でも種類・世代・開閉状態を検査する。再利用したOSの番号が同じでも、古い資源として扱う。
- 任意のユーザーコードをdrop時に呼ぶ仕組みは、初期段階では導入しない。

既存のref世代と資源の開閉状態を混同しない。変数を指すrefが有効でも、その中のFileがclose済みならI/Oは失敗する。
内部の資源表を使う場合は、スロットと世代の再利用、異種資源の取り違え、世代の上限に達した場合の扱いまで決める。
OSハンドルだけの比較を資源の同一性の判定にしない。

### スレッドと終了

資源のスレッド間送信は最初は許可せず、資源の種類ごとに検証してから解禁する。
構造体・enum・リストやクロージャに包んでも、送信制約をすり抜けないよう型検査する。
GUI資源は作成したGUIスレッドだけで操作・破棄する。通常の計算や通信はworkerで行い、値だけをchannelで渡す。

WindowsのGUIスレッドとは、GUIを初期化してイベントを処理するスレッドを指す。
インタプリタの `main` は大きなスタックの別スレッドで動くので、OSのプロセス開始スレッドと同一であることを要求しない。
COM初期化が必要な機能は、このGUIスレッドで初期化・終了する。

現在、`exit` と実行時エラーのネイティブ実行は `_Exit` で終了し、通常の後始末をしない。
この挙動を維持する場合、dropが必ず走るとは約束しない。データの確定には明示的なflush/close/commitを使う。
DBのcommitやファイルの永続化を、終了時の暗黙の後始末に任せない。

## Windowsのウィンドウ・入力・描画

### ウィンドウとイベント

Win32の処理を内部にまとめる。公開APIにHWNDやWindowsのメッセージ番号を出さない。
イベントはOSのコールバックから直接ユーザーコードを呼ばず、イベント列として受け渡す方式を第一案とする。
これにより、描画中や解放中の再入を制御し、イベントの順番をテストできる。

初期段階で必要なイベントは、閉じる要求、サイズ・DPI変更、フォーカス、キー、マウス、文字入力。
キーの押下状態と、文字・IMEの入力は別にする。UTF-16のサロゲートとUTF-8の変換も境界で扱う。
閉じる要求を受けた時点で資源を破棄せず、アプリがイベントを処理した後に解放する。

ゲーム用にはブロックしないイベント取得、GUIの待機時には待つイベント取得を提供する。
時間計測は単調増加する時計を使い、フレーム更新と実際の経過時間を分ける。

### 描画

Direct3D 11とDXGIでデバイス・描画先・表示を管理する。
最初は矩形、三角形、クリップ、画像、文字に限定した2D描画を作り、同じ描画命令をゲームとGUIの双方から使う。
GUIのボタンなどがWin32の個別コントロールを必須とする設計にはしない。

DirectWriteは文字の配置を担当するが、単独で描画先への描画が完結するとは扱わない。
最初はDirect2Dとの相互運用で文字を描く案とし、D3D11/DXGIの描画先を共有する。
ゲーム向けに文字を大量に描く必要が出たら、DirectWriteのグリフをテクスチャへまとめる方式を別途検討する。
D3DとDirect2Dを切り替える順番、flush、EndDraw、Presentの責任を描画基盤に集約する。

- GUIの寸法は論理ピクセル、描画先の大きさは物理ピクセルとして区別する。DPI倍率を取得できるようにする。
- 描画命令を蓄積し、テクスチャ・クリップなどを考慮してまとめて処理する。描画順を勝手に変えない。
- フレームの開始・終了を明示する。前のフレームの一時的な描画先を次のフレームから使わせない。
- サイズ0、最小化、リサイズ、デバイス喪失を状態として扱う。失敗した途中の資源を公開しない。
- Textureや文字用資源は作成したデバイスに属する。別デバイスや再作成前の資源の取り違えを検出する。
- Linux対応時は同じ公開APIに別の実装を接続できるようにする。Direct3D固有の機能を基礎APIへ混ぜない。

### GUI

入力と描画の基盤の上に、レイアウト、フォーカス、ボタン、文字表示、テキスト入力を順に載せる。
ゲームはGUIの部品を使わず、入力・描画・時間だけを直接利用できる構成にする。
日本語の入力欄を完成扱いにする条件には、IME、選択、カーソル、クリップボード、DPI変更を含める。
自前描画のGUIにはアクセシビリティの対応も必要であり、矩形と文字を描けるだけでGUI全体が完成とは判定しない。

## ファイル・通信・PostgreSQL

### ファイル

既存のUTF-8一括読み書きとの互換性を維持する。
バイナリは文字列に混ぜず、まず既存の `u8[]` を候補とする。readはEOFとエラー、writeは実際に書いた長さを区別する。
短い読み書き、空の入力、失敗途中の解放、close後の操作をテストする。
Windowsのパスは内部でUTF-16へ変換し、文字コードと埋め込みNULによる問題を境界で検査する。

### 通信

最初は同期TCP・DNS・タイムアウトを実装する。GUIスレッドをブロックする操作はworkerへ分ける。
公開モジュールはTCP/DNSのstd.netとTLSクライアントのstd.tlsに分け、TCPだけでTLSを要求しない。
短い送受信、EOF、半切断、接続失敗、タイムアウトを区別する。
WindowsではWinsockの初期化と終了、SOCKETの幅、INVALID_SOCKETを内部で扱う。
TLSは検証済みのOS機能または既存ライブラリを使い、証明書と接続先名を検証する。TLS自体は自作しない。
UDP、HTTP、非同期I/OのAPIはこの同期基盤を確かめた後に設計する。

### PostgreSQL

詳細なAPI・状態・トランザクション・配布・検証条件は [PostgreSQLライブラリの設計](postgresql.md) を参照する。

最初はlibpqを利用する案とする。必要なDLL・版・依存DLLの配布方法をalice側で決める。
接続、パラメータ付き問い合わせ、結果取得、明示的なcommit/rollbackを最初の範囲とする。
SQLの値は文字列の連結で渡さず、パラメータとして渡す。
NULL・空文字・バイナリを区別し、接続文字コードと結果の型情報を保持する。
libpqが所有する領域への生のrefを返さず、結果に所有させるかjabberwockの値へコピーする。
パスワードを含む接続情報を、エラーやビルドログにそのまま出さない。

PgConnectionは最初は送信不可とし、worker内で接続を作り、取得した値をGUIへ渡せるようにする。
TLS接続では証明書と接続先名の検証を有効にする。ローカルCIは使い捨てのPostgreSQLで実行する。

## コンパイラ・aliceへの変更箇所

| 箇所 | 必要な変更 |
|---|---|
| Rust版の型検査 | 資源型、ムーブ・借用、送信制約、内部APIの引数と戻り値 |
| インタプリタとIR実行 | 資源の値、操作、解放、エラー、比較実行時の外部副作用の制御 |
| LLVM生成とC runtime | 不透明な表現、資源操作と解放、閉じた値・異種資源・スレッドの検査 |
| 自己ホスト版jwc | 型・IR・LLVM・runtimeの変更を同じ仕様で反映 |
| モジュール読み込み | 標準ライブラリの探索先と、従来のユーザーモジュールとの衝突規則 |
| alice | 必要な内部処理とリンク指定の収集、ネイティブ依存の解決、ビルド指紋 |

ビルド指紋には、ソース・manifestだけでなく、コンパイラ/runtimeの版、資源ABI、対象環境、ビルドオプション、
選んだネイティブ依存を含める。依存の追加・削除や設定変更で古い実行ファイルを使い続けないようにする。
資源型とABIが変わったときの互換性も、ここで管理する。

既存のデバッグ実行はインタプリタとIR、条件によってネイティブでも同じプログラムを実行する。
GUIやDBへの操作を無条件で複数回行わせない。比較試験では独立した使い捨て環境または記録した入力を使い、
実際のアプリの通常実行と分ける。

## 実装の区切りと完了条件

1. **資源管理とビルド基盤**: まずファイルを1種類の資源として実装し、正常終了・失敗経路・明示的close・
   二重close・別名・ムーブ・スレッド制約をRust/IR/ネイティブ/jwcで一致させる。aliceのビルド指紋も検証する。
2. **Windowsのウィンドウと入力**: 作成・イベント取得・閉じる処理・DPI・文字入力を実装する。
   作成と破棄の反復、サイズ0、異なるスレッドからの誤用を検証する。
3. **2D描画**: 図形・画像・文字・クリップ・サイズ変更・デバイス再作成を実装し、ゲーム形式のループ例を動かす。
4. **通信とPostgreSQL**: TCPと接続先を限定した結合試験、libpqでの問い合わせ・トランザクションを実装する。
   GUIからはworkerを経由する実用例を作る。
5. **GUI部品**: レイアウト、ボタン、テキスト入力を載せ、日本語入力とDPIを含めて確認する。

各区切りで実装・テスト・例をそろえる。「ライブラリ全体が完成した」とは区切り単体の完了だけで言わない。
LinuxへのGUI実装、3D描画の公開API、任意のFFI、パッケージ配信サーバーはこの初期範囲には含めない。

## 検証

- 安全性1〜7の既存CIを維持し、資源の誤用と失敗経路を固定攻撃・生成入力へ追加する。
- OSに依存しない資源管理はLinuxでASan/UBSan・MSan・TSanを実行する。GUI相当の資源も模擬実装で検査する。
- Windows CIでは実際のファイル・Winsock・Win32と、D3D11のWARPを使った描画先の読み戻しを検証する。
- 画面表示・IME・フォーカス・DPI変更はWindowsでの対話的な確認も必要。模擬描画の成功で代用しない。
- PostgreSQLは使い捨てDBでNULL・バイナリ・パラメータ・rollback・切断・タイムアウトを検証する。
- 必要なSDK・libpq・描画機能が欠ける環境では、その検証を実行済みと数えない。対応環境と未確認事項を記録する。
